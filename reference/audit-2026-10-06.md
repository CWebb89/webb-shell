Scope: whole tree excluding `reference/` (47 files, ~12.8k lines).

## F1 [Medium] The shell reads and writes Hyprland's `~/.config/hypr/colors.conf`

**Evidence**
- `src/popups/SchemeSwitcher.qml:156-160` — `FileView { path: root.home +
  "/.config/hypr/colors.conf" }`, `parseImage()` extracts `$image = <path>` to
  learn the current wallpaper.
- `bin/matugen-apply.sh:30-31` — after a `matugen color hsl` (hue-wheel) run,
  `sed -i "/^\$image = /d" "$HOME/.config/hypr/colors.conf"` then appends the
  restored wallpaper path.
- The shell already owns the authoritative record: `bin/set-wallpaper.sh:14`
  writes `~/.local/state/webb-shell/background`, and `src/popups/Background.qml:13`
  reads exactly that file.

**Why it matters** — two sources of truth for one fact, and the borrowed one
belongs to another project.
1. On a machine without a Hyprland matugen template that emits `colors.conf`,
   `SchemeSwitcher.currentWallpaper` stays `""`, so `applyCurrent()` returns at
   its guard (`if (!s || !root.currentWallpaper) return`) — the scheme picker
   silently does nothing, with no error shown.
2. `bin/matugen-apply.sh` is `set -euo pipefail`; the `sed -i` on a missing file
   exits 2, so `apply_icon_theme()` never runs and the GTK icon theme silently
   stops following the scheme.

**Fix** — `SchemeSwitcher` reads `~/.local/state/webb-shell/background` through
`ShellConfig` (same file `Background.qml` watches). `matugen-apply.sh` drops the
`colors.conf` write, or at minimum guards it with `[ -f ]`.

**Confidence** — High (both call sites read directly; the file exists on this
machine so the failure path is inferred from `set -e`, not observed).

## F2 [Medium] Keyboard-focus contract is inconsistent across popups

**Evidence** — 21 popups. Nine take keyboard input the proven way, with
`focusable: true` **plus** `WlrLayershell.keyboardFocus: WlrKeyboardFocus.Exclusive`
**plus** a forced-focus timer: MenuPopup (101/106), FindPopup (65/70),
GlancePopup (77/82), WallpaperSwitcher (18/23), SchemeSwitcher (20/26),
ReminderPopup (23/28), PolkitPopup (24/29), LockScreen (19/23), PrintOverlay (18/22).

Six declare `Keys.onPressed` handlers and set **only** `focusable: true`:

| File | Keys handler | Declares |
| --- | --- | --- |
| `src/popups/AudioPopup.qml:120` | Escape | `focusable: true` (108) |
| `src/popups/BluetoothPopup.qml:54` | Escape | `focusable: true` (42) |
| `src/popups/WifiPopup.qml:80` | Escape | `focusable: true` (68) |
| `src/popups/SystemMonitorPopup.qml:39` | Escape | `focusable: true` (27) |
| `src/popups/NotificationCenter.qml:139` | Escape, ↑, ↓, Delete, Backspace | `focusable: true` (127) |
| `src/popups/TrayMenu.qml:130` | Escape, ↑, ↓, ←, Return, Right | `focusable: true` (118) |

**Why it matters** — `NotificationCenter` and `TrayMenu` are not Escape-only:
they implement full list navigation (TrayMenu also a submenu back-stack). That is
a substantial amount of code resting on a contract `AGENTS-REFERENCE.md:27` says
is only "proven" for Menu/Find/Wallpaper, and project memory explicitly warns
"`WifiPopup`/`AudioPopup`/`TrayMenu` omit the last two… treat that as
Escape-only, not as proof that keys route."

Counter-evidence that must be weighed: `WifiPopup.qml:367` pushes focus into the
password field on network click, and Wi-Fi password entry is reported working —
so `focusable: true` alone plausibly yields `WlrKeyboardFocus.OnDemand` and does
route keys. Either the six are fine and the three-line idiom is only needed for
*grab* semantics, or the six are dead. One of the two is wrong today.

**Fix (gated on one runtime test)** — install a probe instance, open the
notification centre via `qs ipc -i <run> call notify center`, send Escape (needs
a key-injection path; `wtype`/`ydotool` are not installed), confirm via
`hyprctl layers -j`. Then either add
`WlrLayershell.keyboardFocus: WlrKeyboardFocus.Exclusive` + a focus timer to the
six, or correct `AGENTS-REFERENCE.md` § "Popup input patterns" and the memory
note.

**Confidence** — High that the inconsistency is real; unverified which side is
correct. No key-injection tool exists on this box, so it needs the user at the
keyboard.

## F3 [Medium] `bin/restart.sh` kills every Quickshell instance on the machine

**Evidence** — `bin/restart.sh:9`: `pkill -f 'quickshell -p '`. The script's own
comment (line 5-6) states this is deliberate: "The pkill pattern matches any
`quickshell -p <path>` form, so it also cleans up duplicates."

**Why it matters** — `~/dev/klipshell` is a second Quickshell project on this
machine, launched the same way. Restarting webb-shell from the menu
(`system.reload.shell`) kills klipshell too, if it is running. The
`~/.local/bin/webb-shell` wrapper already gets this right:
`pkill -f "quickshell -p $SHELL_DIR"`.

**Fix** — the script already computes `SHELL_DIR` (line 8); match on it.

**Confidence** — High.

## F4 [Low-Med] One shared `Process` serialises every menu action

**Evidence** — `src/popups/MenuPopup.qml:366` (`Process { id: runProc }`), used
at `:395` (desktop `runInTerminal`) and `:410` (all `action` rows). A `Process`
refuses a new `command` while running, and the assignment fails silently.

**Why it matters** — `closeMenu()` closes the popup but does not stop `runProc`.
Rows that stay alive after the menu closes therefore block the next action:
`bin/ocr.sh` and `bin/qr-capture.sh` (wait on `slurp`), `bin/pick-color.sh`
(`hyprpicker`), `bin/webapp-install.sh` (`read -rp` prompts), `bin/clipboard.sh`
and `bin/history.sh` (block on a nested `menu-select.sh` session), and the four
`pkg-*.sh` rows (`fzf`). Pick OCR, then re-open the menu and pick anything else
before the region is dragged: the second action is dropped with no feedback.
Memory already names this and prescribes the fix.

**Fix** — detach the long rows in `src/menu/menu.jsonc`:
`"action": "setsid @shellDir@/bin/x.sh >/dev/null 2>&1 &"`. Memory records that a
`setsid … &` child survives the parent bash exiting (verified).

**Confidence** — High on the mechanism; frequency is low (single user, one action
at a time).

## F5 [Low] Two `bash -c` hand-offs interpolate values into shell source

**Evidence**
- `src/popups/MenuPopup.qml:93-94` —
  `"…printf '%s\\n' \"" + key + "\" >> \"$HOME/.cache/webb-shell/app-usage\""`.
  `key` is a `.desktop` id or a menu id; a `"`, `$` or backtick in a `.desktop`
  filename would execute.
- `src/popups/MenuPopup.qml:306` (`writeResult`) interpolates the IPC-supplied
  `Popups.dmenuSelectionFile` / `dmenuDoneFile` paths into the same shape.

**Why it matters** — every other shell hand-off in the repo uses the safe
positional form (`Reminders.qml:137`, `NotificationCenter.qml:52`,
`NotificationHistory`-consumers, `TrayMenu`): `["bash","-c", script, "--", arg]`.
These two are the outliers. Practical risk is low (single user, own files), but
the pattern should not spread.

**Fix** — pass `key` and the two paths as positional arguments.

**Confidence** — High (code reads directly).

## F6 [Low] `Background.qml` reloads a nonexistent file once a second, forever

**Evidence** — `src/popups/Background.qml:58-63`:
`Timer { interval: 1000; repeat: true; running: root.currentBackground === ""; onTriggered: root.backgroundFile.reload() }`.

**Why it matters** — the poll exists for a documented real reason
(`FileView.watchChanges` only establishes a watcher for a file that exists at read
time). But on a machine where no wallpaper has ever been picked, `currentBackground`
stays `""` and this never stops. ~3600 `reload()` calls/hour for the life of the
shell, against the project's own rule ("no subprocess-spawning poll on an
always-on timer" — this one is not a subprocess, so the cost is small, but it is
unbounded).

**Fix** — bound the attempts (e.g. 30 ticks) and stop; the first wallpaper pick
populates the watcher anyway.

**Confidence** — High that the timer is unbounded; low that the cost matters.

## F8 [Low] `bin/webapp-install.sh` and `bin/open-file.sh` hardcode an app

**Evidence**
- `bin/webapp-install.sh:29` — `Exec=chromium --app="%s"`.
- `bin/open-file.sh:26` — `exec kitty -e "$terminal_app" "$file"`.

**Why it matters** — `bin/xdg-default.sh get web|term` already resolves both
roles from XDG defaults (and `binds.lua` uses it). On another PC with a different
browser or terminal these two break, and they are exactly the kind of thing the
other-PC install has to work around.

**Fix** — `"$(dirname "$0")/xdg-default.sh" get web` / `get term`, with the
existing hardcoding as fallback.

**Confidence** — High.

## F9 [Low] `install.sh`'s tool check misses tools the shell runs

**Evidence** — `install.sh:29-38` claims "The tool lists below mirror what the
shell and the compositor actually run, verified against every caller in `src/` and
`bin/`." A scan of external commands invoked from `src/`, `bin/`, `shell.qml`,
`Bar.qml` finds these absent from all three lists (`CORE_TOOLS`, `OPT_TOOLS`,
`COMPOSITOR_TOOLS` + `jq`):

`xdg-mime`, `xdg-settings` (2 call sites each), `gio` (6 — `xdg-default.sh`,
`open-file.sh`), `ffmpeg` (4 — `transcode.sh`), `hyprpicker` (6 — `pick-color.sh`),
`stat` is coreutils but is the search backend's critical dependency.

Also: `README.md:41-43` lists **`qrencode`** as a requirement for the QR menu row,
but `qrencode` appears nowhere in the repo — `bin/qr-capture.sh` *decodes* with
`zbarimg`.

**Fix** — add the missing names to `OPT_TOOLS`; delete the `qrencode` claim.

**Confidence** — High.

## F11 [Info] Cost notes, not defects

- `src/popups/SystemMonitorPopup.qml` runs a 20 Hz repaint
  (`Timer { interval: 50 }` + `spark.requestPaint()` for the glow "breathing"),
  plus a 2 s canvas sample animation. Only while the panel is open, and the shell
  renders on Qt's basic main-thread loop — it is the heaviest open-only widget.
- `bin/scheme-swatches.sh` spawns ~17 `matugen` processes per regeneration
  (1 default + 6 resize-filter source extractions + 10 scheme renders). Gated on
  a wallpaper/mode change by `SchemeSwitcher.regenerate()`'s `lastRegen*` guard,
  so it is not a steady-state cost.
- `src/popups/AudioPopup.qml:479,581` — `signal picked(string name)` /
  `signal pickDevice(string name)` actually receive a pactl *index*. QML coerces
  number→string and `setDefaultSink` stringifies anyway, so it works; the declared
  type is a lie. Same shape at `PortChip.picked` (that one is a real name).
- `MenuPopup` has no scrim/outside-click dismissal (unlike every other panel).
  `AGENTS-REFERENCE.md` documents this as intentional for the keyboard overlays.
- `shell.qml:263` `IpcHandler{target:"menu"}` `toggle` sets `menuOpen` without
  `Popups.closeAll()`, unlike every other `toggle`. Opening the menu over an open
  Wi-Fi/audio panel stacks the fullscreen, mask-less menu surface over that
  panel's still-open scrim; selecting a hand-off row then closes the menu and
  leaves the panel open. Arguably the intended hand-off flow — flagging only
  because it is the one `toggle` that breaks the pattern.

## Verified clean

- `Popups` exclusivity: all 10 menu `open`/`toggle` targets resolve to real
  `Popups` keys via `handOff()` (`notif` → `notifOpen`, `clock` → `clockOpen`,
  `toggle:bar` → `ShellState.barVisible`).
- Every `@shellDir@`-referenced script in `menu.jsonc` exists and is executable.
- `MenuPopup.menuData` default is a valid empty model (`MenuModel.parse("")`).
- Every centered popup card carries `opacity: Popups.XOpen ? 1 : 0` — the
  input-blocking regression documented in memory is not present anywhere.
- `pgrep -f` patterns: the only boot-time one is `Recorder.qml:26`, correctly
  `[-]`-escaped; `menu.jsonc:300` uses the escaped form too.
- Guard batching: one `bash` process per evaluation, `guardPrelude()` caches
  `pacman -Qq`; `checked` and `disabled` sharing a string cost nothing extra.
- Qt.callLater is not used as a delay anywhere; `Delay.run` is used for all delays.
- `src/assets/pam.d/webb-shell` ships and `install.sh` installs it.

## Live observation made during the audit

`~/.local/state/webb-shell/background` was **0 bytes** (mtime 2026-10-06 06:08)
while `~/.config/hypr/colors.conf:102` still read
`$image = /home/cwebb/Pictures/Wallpapers/honda.gif`, and the live shell had been
up since the previous evening. Consequences at that moment: `Background.qml`
drew no wallpaper (flat themed color), its 1 Hz probe was running continuously
(F6 in the wild), and only the `colors.conf` path kept the Scheme picker's
`currentWallpaper` non-empty.

F1 and F6 remove both dependencies, but the record itself still has to be
written once: picking a wallpaper (`SUPER + W`, Enter) re-creates it. Until then
the background stays flat and the Scheme picker's apply is a no-op.
